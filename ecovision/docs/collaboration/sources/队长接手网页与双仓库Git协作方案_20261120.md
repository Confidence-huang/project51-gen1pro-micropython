# 移远杯：队长接手网页与双仓库 Git 协作方案

> 方案日期：2026-11-20。对象：网页仓库 `project51-classroom-dashboard`、板端仓库 `project51-gen1pro-micropython`，以及队长 AI 要学习的 `agent-git-discipline`。本文是待双方采纳的协作方案；没有代替队长登录 GitHub、安装 Skill、改变仓库权限或部署服务。

## 1. 先看清系统和当前事实

```text
STM32 + EC200U → EMQX Cloud（MQTT）→ 队长阿里云 ECS（历史与 AI API）

GitHub Pages 静态看板 ← 浏览器读取 HTTPS API
```

- [网页仓库](https://github.com/Confidence-huang/project51-classroom-dashboard)负责前端、网页测试、`docs/` 发布包，以及相关服务端源码。公开网页是 <https://confidence-huang.github.io/project51-classroom-dashboard/>。GitHub Pages 当前从 `main` 的 `/docs` 发布；这已经在 GitHub 设置接口核对。GitHub Pages 不能替代 MQTT Broker 或 ECS 上的 Node 服务。

## 2. 队长接手网页：按这个顺序验收

### A. 本机只验页面与代码

队长在自己电脑安装 Git、Node.js、PowerShell 7，然后克隆网页仓库。Node 版本以 `package-lock.json` / Vite 安装要求为准；不要直接沿用历史文档给本机历史服务写的 Node 26 要求。仓库有 `package-lock.json`，所以用 `npm ci`。

```powershell
git clone https://github.com/Confidence-huang/project51-classroom-dashboard.git
Set-Location .\project51-classroom-dashboard
git rev-parse --show-toplevel
git status --short --branch
git log -1 --oneline
node --version
npm ci
npm test
npm run dev
```

打开 Vite 终端打印的本机地址，通常是 `http://127.0.0.1:5173/`。检查页面能加载、布局无明显缺失、设置和 AI 助手入口能打开；将终端输出与浏览器错误留作记录。`npm run dev` 是本地网页服务，不会部署 GitHub Pages，也不需要队长先登录 ECS。

**当前已知限制：**API 对 `https://confidence-huang.github.io` 返回跨域许可，但对 `http://127.0.0.1:5173` 不返回。因此本地 Vite 页面可能无法直接显示云端实时数据，即使 API 本身正常。不要为此把 MQTT/DeepSeek 密码塞进网页；也不要把“本地页面能打开”写成“端到端验收通过”。若确实要让 localhost 做全链路联调，另开 Issue，评估临时允许 localhost 或本地代理的单独改动与关闭条件。

### B. 线上验真实链路

1. 打开 [公开看板](https://confidence-huang.github.io/project51-classroom-dashboard/)，确认无须输入 MQTT 密码就能查看页面。
2. 打开 [只读遥测 API](https://api.careerpathdesk.com/api/telemetry) 和 [AI 状态 API](https://api.careerpathdesk.com/api/agent/status)，记录 HTTP 状态、`broker_connected`、最新 `seq`、样本时间及历史条数，不转发任何敏感内容。
3. 对照网页最新值与 API 的 `seq`/时间。界面必须明确区分“实时／过期”“实板／模拟”；K230 人数未接入时允许显示空值，光敏未标定时只能标 ADC 原码，不能写成 lx。
4. 手动点开 AI 助手，先用“状态测试”核对后端连通。若要实际提问，先确认本次测试允许消耗模型额度，再问一个与现有样本有关的问题；核对回答是否说明数据来源与缺失字段。不要把一次 AI 回答当作硬件实测证据。
5. 打开手机或另一台电脑再访问公开页，记录页面是否正常。若网页失败，分别定位 Pages 发布、浏览器控制台、API、ECS 服务、EMQX 和板端；不要直接重启或改配置。

**队长交付的最小验收记录：**日期时间、网页 URL、Pages/接口可达性、本地 `npm test` 结果、最新样本 `seq` 与时间、页面截图、是否看到模拟/过期标记、故障复现步骤。凭据、私钥、`.env`、个人数据均不截图、不发群。

### C. 只有改网页时才构建发布包

`npm run build` 会更新仓库内被 Pages 发布的 `docs/`，因此只在自己的特性分支和明确的网页改动任务中运行。先跑 `npm test`、再构建、检查 `docs/` 是否对应本次源码，随后由 PR 审查合并到 `main`；Pages 才会发布 `main:/docs` 的版本。不要在板端仓库跑网页构建，也不要在共享 `main` 上直接试改。

## 3. 双方角色与交接物

| 角色 | 主要负责 | 提交与验收边界 |
| --- | --- | --- |
| 你（现有主要开发者、仓库所有者） | 前端/板端接口合同、主要功能、版本与公开发布决策；审查队长提交 | 决定是否合并和发布；涉及板端真机/固件动作按项目既有实物规则执行 |
| 队长（ECS 持有人、协作者） | 本机跑通网页、线上可用性验收、ECS 服务状态与错误定位、维护可复现运行说明；审查你的 PR | 一项问题一张 Issue；在自己的分支提交，向两仓分别开 PR；未经共同确认不改板端协议、生产密钥或服务配置 |
| 各自的 AI | 按 Skill 检查 Git 边界、协助实现/测试/写 PR 草稿、解释日志 | AI 使用各自机器与各自 GitHub 身份；遵守明确授权，不共享你的登录态，也不能代替人批准自己的 PR |

先让队长只处理网页“运行说明与验收”Issue；板端仓库先以只读学习为主。跨仓接口改动应拆为两个 Issue 和两个 PR，用同一个接口约定文档链接关联，明确先后兼容顺序。生产 ECS、EMQX、Cloudflare 的故障定位由队长负责，涉及公开 API 行为变化时你要参与 Review。

## 4. 让队长 AI 真正学会并执行 Git Skill

技能来源是独立的 [agent-git-discipline 仓库](https://github.com/Confidence-huang/agent-git-discipline)，不是网页或板端仓库的一部分。2026-11-20 核对的来源 `main` HEAD 为 `fa49c87d4fb1d35b6428ac2a7504a75a09015a55`。队长先完整克隆来源，核对 `.git`、`origin`、HEAD、目录清单，再读 `README.md`、`skills/git-discipline/SKILL.md`、其 `references/`、`docs/03-Agent适配.md`、`docs/05-提交与PR流程.md` 和适用的托管块配置；不要只给 AI 一张截图或复制几行摘要。版本以后升级时先 `fetch`、看 diff、验证，再更新 AI 入口。

如果队长用截图里的 **Antigravity**：其适配文档记录了 `skills.json` 引用技能**父目录**的方式（父目录下一层应是 `git-discipline/SKILL.md`）；Antigravity 不跟随 Junction/软链，不能只建链接就声称加载成功。实际路径按队长机器填写，例如 `<克隆目录>\agent-git-discipline\skills`，在用户级 `%USERPROFILE%\.gemini\config\skills.json` 或工作区 `.agents\skills.json` 中引用。让队长 AI 在一个只读会话中说出 Skill 文件实际路径、当前 commit、三条禁止操作，再核对本机配置能否被发现。若用 Codex 或其他 AI，则按该 Skill 的 `docs/03-Agent适配.md` 对应小节配置，不假设所有 Agent 都自动读取 `AGENTS.md`。

板端仓库已带项目级 `AGENTS.md` 和 `PROJECT_LOG.md`，网页仓库当前没有这两个文件；队长单独克隆网页仓库后不会自动得到本机父目录 `Project_51` 的规则。首批可在网页仓库用独立 PR 加入面向队友的 `AGENTS.md`、运行说明和简要日志入口；写入前先讨论最小内容，不复制你个人电脑路径或用户级规则。来源 Skill 目前提供 v6 模板，板端项目仍使用 v5 托管块；升级托管块版本应作为单独 PR 对比审查，不能自动覆盖。

可直接发给队长 AI 的第一条任务：

```text
请先做只读接手，不改代码或 GitHub 设置。完整读取 agent-git-discipline 来源仓库的 README、skills/git-discipline/SKILL.md、references/ 和 docs/03-Agent适配.md、docs/05-提交与PR流程.md，报告来源 remote、HEAD 和 Skill 的实际路径。然后分别核对 project51-classroom-dashboard 与 project51-gen1pro-micropython 的 Git 根、branch、HEAD、index、工作树和 origin；先读板端仓库的 PROJECT_LOG.md/AGENTS.md，也核对网页仓库是否存在项目级规则。按方案在网页仓库执行 npm ci、npm test、npm run dev，记录本地页面与线上 GitHub Pages/API 的验证结果，不把 localhost 跨域失败误判为 API 故障。列出拟开的 Issue 和首个文档 PR 的范围，等待我确认任何新建分支、push、PR、ECS 配置或秘密写入。严禁 git add . / git add -A、泄露凭据、清理已有未跟踪文件和直接改 main。
```

这段提示词只授权只读检查和本机运行；队长可根据自己的 AI 与 Skill 授权规则，单独授权明确仓库/分支/远端动作。你的本机长期授权不会自动转移给队长 AI。

## 5. GitHub 权限、分支与审查规则

**加入方式：**两仓都是 `Confidence-huang` 个人账户下的公开仓库。队长可以先用自己账号 fork 后提 PR，完全不需要你的凭据；需要共同在原仓库推自己的分支时，由仓库所有者在每个仓库 `Settings → Collaborators → Add people` 分别邀请队长 GitHub 用户名，并等待他接受。个人仓库 collaborator 具备写入能力，不能把“被邀请”理解为只能读；所以先以 fork 试运行也合理。不要共享账号、PAT、SSH 私钥、ECS root 密码。GitHub 仓库协作权限与 ECS 的 `sudo` 是两套独立权限。

**分支：**`main` 只放可复现基线。每张 Issue 从最新 `main` 开一个短期分支，例如 `docs/17-captain-runbook`、`fix/24-telemetry-time`。同一个功能分支只解决一张 Issue；网页与板端必须各在自己的 Git 根执行命令。新建/切换分支、push、开/改/合并 PR 等，在队长 AI 会话中先取得精确授权。当前两仓没有实际启用 `main` 保护；“通过 PR 合并”目前是约定，尚非平台强制。建议队长完成第一张练习 PR 后，由所有者在两仓设置 `main` 规则：禁止直接推送、至少 1 位**其他人**审查、阻止 force push/删除；有真实 CI 后再设为必需检查，避免设置一个不存在的检查导致无法合并。

**提交：**改前记录 `git rev-parse --show-toplevel`、分支、HEAD、`git status` 和目标文件归属。一个可独立回退的逻辑改动一个 commit；只 `git add <本轮文件>`，复核 `git diff --cached`，跑对应测试后本地 commit。每个仓库独立用 `git rev-list --first-parent --count HEAD` 记“第 N 次 git”及 SHA。本地 commit 权限按执行者自身会话授权；Skill 的默认本地提交规则不等于自动允许远端写入。推送后用 `git ls-remote origin <分支>` 对照本地 SHA；网络异常时不凭 `Everything up-to-date` 判断成功。

**Issue：**标题写可观察问题，例如“网页：队长本机无法显示实时数据”；正文写现象、复现步骤、预期/实际、验收标准、负责人与仓库、证据等级（真实设备/线上 API/本机模拟）。不要把密码、日志中的敏感字段贴进去。跨仓任务互相链接两个 Issue，避免把两个仓库混在一个 PR。

**PR：**标题只描述一个动作，例如 `docs: 补充队长网页运行说明`。正文至少包含关联 Issue、变化范围、实际测试命令与结果、线上/本机/模拟证据边界、截图或输出、风险和 `git revert <SHA>` 回退思路。提出者不能作为唯一审查者；队长改网页由你 Review，你改 ECS 相关前端/API 或板端接口由队长 Review。Review 提出具体文件与可复现原因；修改后重新跑测试、更新 PR，再由另一人批准。合并后的 Pages 页面要再看一次，因为本地构建成功不等于线上成功。

**优先落地顺序：**① 网页运行说明 PR（纠正过时 README，保留当前部署事实）；② 网页 CI PR（至少 `npm ci`、`npm test`、`npm run build`，检查构建产物与源码一致）；③ 两仓 `main` 规则；④ 板端仓库按实际共同修改需求再设 CI/审查约定。不要为建制度先改板端固件。

## 6. 每次同步与冲突处理

```text
开始任务 → 核对真实仓库/工作树 → fetch → 确认自己的改动安全 → 更新 main
        → 从 main 建任务分支 → 小改动/测试/原子提交 → 请求授权 push/PR
        → 他人 Review → 合并 → 再取回 main → 线上验收
```

在**干净**工作区更新本地 `main` 可用：

```powershell
git fetch origin
git status --short --branch
git switch main
git pull --ff-only origin main
```

如果有未提交改动，先查归属：别人的内容不提交、不丢弃、不 `git clean`；自己的改动先按任务原子提交，或在得到相应授权后暂存。若分支落后 `main`，先 `fetch` 并对比；原则上在自己分支合入最新 `origin/main`，冲突由该分支作者逐文件解决，另一人 Review。对已推送的共享分支不随意 rebase/强推。网页 `src/`、`docs/` 若同时冲突，由网页任务负责人重新构建 `docs/` 并核对，而不是手工挑选旧压缩产物。跨仓接口冲突先固定 JSON 字段、单位、空值与版本，再分别修改两仓；不能靠“哪一边先 push”裁决。误合并优先用新的 revert PR，保留审计历史。

- [ ] 用自己的 GitHub 账号看见两仓，确认网页仓库 `main`、Pages 地址与 `main:/docs`。
- [ ] 完整克隆 Git Skill，给自己的 AI 配置入口，要求 AI 回报实际 Skill 路径与 commit。
- [ ] 克隆网页仓库，记录 Git 根、HEAD、工作树；不动已有未跟踪内容。
- [ ] 跑 `npm ci`、`npm test`、`npm run dev`，在本机打开网页并记录结果。
- [ ] 用公开 Pages 网站和两个只读 API 核对线上最新数据与 AI 状态；注明本机跨域边界。
- [ ] 在网页仓库建“更新运行说明”Issue，写清复现/验收与当前 README 的过时段落。

完成标准是队长能独立说清“页面从哪里运行、数据从哪里来、怎么判断它真的工作、如何发起一项可审查的改动”。完成网页接手后，才安排板端仓库的具体共同开发 Issue。
